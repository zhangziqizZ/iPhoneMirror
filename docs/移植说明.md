# iPhoneMirror 鸿蒙 PC 移植说明

> 本文件面向维护者。它回答三个问题：**哪些是上游原封不动的代码**、**哪些是本移植新增的**、
> **哪些还没做以及为什么**。每一项结论都附了可复跑的验证方式，不靠"看起来对"。

---

## 0. 一句话结论

本工程不是"照着重做一个投屏应用"，而是把上游 iPhoneMirror 的**协议栈、采集状态机与
解码帧模型整棵搬过来**，只为鸿蒙补一层平台实现——与上游自己的 Linux 移植分支
（`iPhoneMirror-linux-port`）用的是同一套手法。

| 项 | 数量 |
|---|---|
| 上游文件（逐字保留、零改动） | 参与编译 14 个 / 整棵 Core 树 109 个文件、27 926 行 |
| 本移植新增的平台层 | 12 个 `.cpp`（3 304 行）+ 头文件（807 行） |
| UI 布局 | 上游是 WPF（`net10.0-windows`，`MainWindow.xaml` 2136 行），**无法在 OHOS 渲染**；按原版逐控件对照还原为 ArkTS（`pages/Index.ets` 1644 行，22 个 `@Builder`，详见 4.4） |
| UI 图标 | 原版 30 处 `ui:SymbolIcon`（= Fluent System Icons）→ 27 个上游 SVG 随工程落地（`tools/fluent-icons/`），生成为 28 条矢量路径（`common/FluentIcon.ets`），**坐标一个不改** |
| UI 配色 | `SharedUI/Themes/DarkTheme.xaml` 130 行 → `common/Theme.ets` 137 行，**色值一个不改** |
| UI 文案 | `Strings.zh-CN.xaml` 747 行逐字取用，仅 4 处平台措辞最小替换（见 4.4） |
| 真实 NDK 下的编译结果 | **25 / 25 翻译单元通过，0 警告** |
| 真实 NDK 下的链接结果 | `-Wl,--no-undefined` 成功，动态符号表含 **57 个 `im_*` 导出** |
| 构建层垫片运行时自检 | **52 项全通过**（在鸿蒙 PC 上真实运行） |

> 「只有 UI 的**布局层**不能逐字节复制」，原因与证据见 **4.4**：上游 UI 是 WPF，OHOS 没有 .NET 运行时；
> 上游自己的 Linux 分支也没移植它，而是另写了个自称 *"the minimal Linux shell"* 的 Avalonia 壳。
> 本移植不沿用那个"极简壳"，而是**按 `MainWindow.xaml` 逐控件还原**完整界面，
> 并把图标与配色这两层**原样搬过来**（坐标与色值都不改）。

## 1. 硬规则

来自上游 `docs/LINUX_PORT.md`，本移植原样继承：

> **对上游既有文件只允许做接口抽取，不允许夹带行为变更。平台相关一律新增文件。**

具体到本工程，就是三条不可协商的纪律：

1. `entry/src/main/cpp/Core/` 是上游 `src/Core/` 的**逐字节拷贝**，一行都不改，也不加
   `#ifdef`。
2. 鸿蒙所需的一切都放 `entry/src/main/cpp/ohos/`，命名 `Ohos*.cpp` / `Ohos*.h`。
3. 上游文件用到了而 OHOS 工具链**缺**的语言设施（`std::format` / `std::jthread` /
   `std::stop_token`）与系统头可见性差异，一律在**构建层**用垫片补齐
   （`ohos/compat/`），不改上游一行。

第 3 条是这套方案能不能成立的关键：如果允许改上游，那就不叫移植了。

## 2. 移植基线

工作区里有两份上游：

| 目录 | 角色 |
|---|---|
| `iPhoneMirror-linux-port` | **骨架来源**。它已经把上游拆成"平台中性 / Windows 专用 / Linux 专用"三套源列表，并把接缝（`Media/IVideoDecoder.h`、`Audio/IAudioRenderer.h`、`Media/ActiveVideoDecoder.h`、`Transport/QtUsbTransport.h`）抽出来了 |
| `iPhoneMirror-main` | Windows 原版，用来核对 C ABI（`CoreApi.h`）、`ApiVersion` 与资源 |

为什么以 Linux 版为骨架：**它是同一上游的移植分支，等于上游作者亲手做过的"如何给新平台
换后端"的示范**。照它的分层做，鸿蒙这一层就只是"再换一次后端"，而不是"重新设计"。

> 上游 Linux 版的 `docs/LINUX_PORT.md` 记录了 P0–P7 的阶段划分、`uaccess` ACL、
> usbmuxd 竞争、以及 `CaptureSession.cpp` 的"两平台共用 2402 行握手状态机"决策。
> 本移植的取舍直接对齐那份文档。

### 4.3 未实现 —— 明确报错，绝不假成功

C ABI 有 57 个导出，其中 **29 个是真实实现**，**28 个返回明确的失败码**
（`CaptureBackendUnavailable` + 一条说明缺什么、归属哪个阶段的 `last_error`）。

上游 `LinuxCoreApi.cpp` 里写着这条规矩，本移植照做：

> **任何导出都不允许"没做却报成功"。**

| 类别 | 未实现项 | 原因 |
|---|---|---|
| 多设备会话 | `im_session_*` 共 17 个 | 上游 Windows 版支持多会话；本移植先跑通单设备路径。`im_session_destroy` 是空动作（没有会话可销毁），不假报成功 |
| AirPlay 无线接收端 | `im_wireless_receiver_*`、`im_media_cast_*`、`im_refresh_wireless_devices`、`im_wireless_session_create` 共 8 个 | 需要随包移植上游的 UxPlay 派生宿主（`UxPlayHost/`、`WirelessHost/`），属独立工作项 |
| 图像调节 / 圆角 / 旋转 | `im_set_image_adjustments`、`im_set_preview_corner_profile`、`im_session_set_window_rotation` | 预览着色器尚未接亮度/对比度/饱和度/gamma 与圆角裁剪 |
| 带选项启动 | `im_start_capture_with_options` | 采集本身能跑（`im_start_capture` 已实现），但 `CaptureOptions` 的逐字段映射是独立工作项；一边启动一边悄悄丢掉一半选项正是本文件拒绝制造的假成功 |

> 注意 `im_get_capture_status` 的行为：查询本身失败时返回 `-1` 而不是伪装成 `Idle`；
> 桥接层（`napi_bridge.cpp`）也如实把它转成 `state: -1` 交给 ArkTS。

### 4.4 UI 层 —— 原版是 WPF，只能逐项还原而不是逐字拷贝

这是本次移植里**唯一无法"逐字节复制"的一层**，必须说清楚，否则会被误解成偷工减料。

**上游 UI 的技术栈**

| 项 | 事实 |
|---|---|
| 项目文件 | `src/App/iPhoneMirror.App.csproj` → `TargetFramework net10.0-windows10.0.19041.0`，`UseWPF=true`，`WPF-UI 4.3.0` |
| 主窗口 | `src/App/MainWindow.xaml` **2136 行** |
| 子窗口 | `src/App/Windows/*.xaml` **17 个、共 2296 行** |
| 本地化 | `src/App/Localization/Strings.{zh-CN,en-US,zh-HK}.xaml` **各 747 行** |
| 主题 | `src/SharedUI/Themes/DarkTheme.xaml` **130 行**（`App.xaml` 里 `Theme="Dark"`） |
| 图标 | 主窗口 30 处 `<ui:SymbolIcon Symbol="…" FontSize="…"/>`，即 **Fluent System Icons** |
| 代码量 | 全仓 128 个 `.cs`、38 个 `.xaml` |

**结论：XAML 在 OHOS 上无法渲染。** OHOS NEXT 没有 .NET / CoreCLR 运行时，
也没有 WPF 的渲染栈。这不是"不想移"，是物理上不存在承载物。

**上游自己的 Linux 版是怎么做的（重要旁证）**

上游官方 Linux 分支并没有移植这套 UI：

- `src/App/` 的 WPF 工程**原样保留**，`TargetFramework` 仍是 `net10.0-windows10.0.19041.0`；
- 另建 `src/LinuxShell/`，用 **Avalonia 12.1.1** 写了一个壳，其 `.csproj` 注释是项目自己的原话：

  > `P5a: the minimal Linux shell. It imports the preview surface the Core library exports`
  > `and shows it, which is the last seam in M1.`

  即：官方跨平台时给 Linux 用户的也是 **"minimal shell"**，而不是那 2136 行的完整界面。

**本移植的做法：把 UI 的三个可搬部分全部照搬**

"逐字拷贝 XAML"不可能，但 UI 并不是只有 XAML 一层。除了布局本身，**图标、配色、文案
都是数据，可以原样搬**。本移植就是按这个思路做的：

| 层 | 来源 | 落点 | 忠实度 |
|---|---|---|---|
| 布局 | `MainWindow.xaml` 2136 行 | `pages/Index.ets` 的 22 个 `@Builder` | 逐控件对照，含顺序、内外边距、圆角、字号 |
| 图标 | 30 处 `ui:SymbolIcon` | `common/FluentIcon.ets`（419 行）+ `tools/fluent-icons/` 的 27 个 SVG | **矢量路径逐点一致**，坐标一个不改 |
| 配色 | `DarkTheme.xaml` 130 行 | `common/Theme.ets`（137 行） | **色值一个不改**（含 `#AARRGGBB` 的 alpha） |
| 文案 | `Strings.zh-CN.xaml` 747 行 | 直接内联在 `Index.ets` | 逐字取用，4 处平台措辞最小替换（见下） |

**① 图标：不是"找个相似的替上"，是把图标本身搬过来**

WPF-UI 的 `SymbolIcon` 渲染的是 Fluent System Icons 字体里的码点。鸿蒙没有这个字体，
但每个图标本身就是一段纯矢量路径（MIT 开源）。所以：

```
tools/fluent-icons/*.svg            ← 原封不动的上游 SVG（27 个，来自 fluentui-system-icons）
        │  tools/gen_fluent_icons.py（自动生成，避免手抄坐标）
        ▼
common/FluentIcon.ets               ← 28 条路径（27 个字体图标 + 1 个手绘轮廓）
        │  FluentSymbol({ iconName, iconSize, iconColor })
        ▼
Shape.viewPort（= SVG 的 viewBox）+ Path.commands（= path d）
```

两个关键细节：

- **`Shape.viewPort` 就是 SVG 的 `viewBox`**：把逻辑坐标映射到组件实际尺寸，
  所以 `iconSize` 改变时图标等比缩放，与 WPF 的 `Stretch` 行为一致。
- 原版有一处图标**不是** `SymbolIcon`，而是 `MainWindow.xaml:1270` 内联的手绘手机轮廓
  （`<Path Width="38" Height="48" Data="M13,2 … Z M15,7 L23,7" StrokeThickness="2"/>`）。
  它以 `FluentSymbol({ iconName: 'DeviceOutline', outline: true })` 还原 —— 同样坐标不改，
  并用 `strokeWidth(2)` + `strokeLineCap(Round)` 对应原版的 Stroke 画法。

30 处 `SymbolIcon` 的 `Symbol` 名与 `FontSize` 全部照用（`PhoneDesktop24`/20、
`ProjectionScreen24`/20、`Dismiss20`/16、`Screenshot20`/15、`WindowNew20`/14、
`MusicNote220`/38 …），没有按鸿蒙习惯替换成别的图标。

## 5. 构建层垫片（`ohos/compat/`）

这是"上游一行不改"这条硬规则的全部代价所在。缺口清单是**实测**出来的，不是猜的：

### 5.1 语言设施缺口

用真实 SDK 读 feature-test 宏：

```bash
clang++ --target=aarch64-linux-ohos --sysroot=<sysroot> -std=c++20 \
        -E -dM -include version -xc++ /dev/null | grep __cpp_lib_
```

| 设施 | OHOS libc++（clang 15 / API 26 SDK） | 上游谁在用 | 垫片做法 |
|---|---|---|---|
| `std::format` | **缺**（无 `__cpp_lib_format`） | `Logging.cpp`、`CaptureSession.cpp`、`Socket.cpp`、`Ohos*` 等 | `ohos_cxx_compat.h` 内自制解析器；`compat/format` 拦 `#include <format>` |
| `std::jthread` / `std::stop_token` | **缺**（无 `__cpp_lib_jthread`） | `CaptureSession.cpp`、`Logging.cpp` | 同文件内等价实现（析构 request_stop + join，首参传 stop_token） |
| `std::counting_semaphore` | 有（`__cpp_lib_semaphore = 201907L`） | — | `compat/semaphore` 用 `__has_include_next` 让路；垫片分支自动失效 |
| OpenSSL EVP（SHA-256） | **无** | `Logging.cpp` 的 `fingerprint()`（设备序列号匿名化） | `compat/openssl/evp.h`，内含自足 SHA-256（NIST FIPS 180-4） |
| `libusb.h` | **无** | `Transport/QtUsbTransport.h`（被 `AppleUsbIdentityCache.h` 传递包含） | `compat/libusb.h` 提供**纯类型声明**（`libusb_context` 等不透明指针） |
| `wchar_t` | 4 字节 | ABI 沿用宽字符（上游 D2 决策） | 无需垫片，实测 `sizeof(wchar_t) == 4` |

垫片的每一段都写成 `#if !defined(__cpp_lib_xxx)` 保护，**工具链补齐后自动失效**，
上游代码无需任何改动即可切回标准实现。

### 5.2 系统头可见性差异

OHOS 用的是 musl 头文件，与 glibc 有行为差异，实测到的只有一处：

| 现象 | 受影响的上游文件 | 垫片做法 |
|---|---|---|
| `<sys/socket.h>` 不像 glibc 那样顺带引入 `<sys/select.h>`，导致 `fd_set` / `timeval` / `::select` 全部找不到声明 | `Transport/Socket.cpp`（209/212/213/232/233 行） | `ohos_cxx_compat.h` 里补 `#include <sys/select.h>`。系统头本就存在，只是"引入"而非"自制声明" |

### 5.3 垫片自身的正确性

自制的 `std::format` 是**行为**风险最大的部分，所以做了运行时自检
（`tools/shim_selftest.cpp` + `tools/shim_selftest.sh`，在鸿蒙 PC 上直接跑）：
覆盖上游实际用到的每一种格式（`{}`、`{:X}`、`{:x}`、`{:08X}`、`{:016X}`、`{:04X}`、
`{:02x}`、`{:08x}`、`{:.3f}`、`{:.2f}`、多占位符、转义花括号、`string_view`/`uint64` 实参），
以及 `std::jthread` 的 stop_token 传递、析构自动 join、移构语义、`counting_semaphore` 的阻塞/唤醒。

顺带修掉了两个垫片自身的 bug（都是自检发现的）：

- `std::format` 原来把实参存成 `const std::decay_t<Args>&` 引用，字符串字面量会绑定到
  "数组→指针"转换产生的临时量上，**语句结束即悬空**；且 `const Args&` 形参会吃掉数组
  元素类型的 const，使 `decay_t` 得到 `char*` 而对不上。改为转发引用 + `std::make_tuple`
  按值存 decay 后的实参。
- 垫片把 `request_stop()` 标了 `[[nodiscard]]`，而**标准里它不是**，导致上游
  `Logging.cpp` / `CaptureSession.cpp` 里"确实不关心返回值"的调用点凭空冒出
  `-Wunused-result` 警告。垫片的职责是复现标准行为，不是比标准更严。

### ArkTS 侧：在本地复现 `CompileArkTS`

`hvigor` 装在 `/data/app/hvigor.org/`（沙箱外，`Permission denied`），本机跑不了
真构建。但 `CompileArkTS` 报的错里绝大多数是**纯 TypeScript 语义错误**——
例如 `Property 'maxWidth' does not exist on type 'TextAttribute'`——完全可以本地查。

关键发现：SDK 自带的 `ets-loader` 里有一份 **OpenHarmony 打过补丁的 TypeScript**
（`typescript@4.9.5-r4`），它认得 ArkTS 的 `struct` / `@Component` / `@Builder`
语法。于是把三样东西拼起来，就等价于 `CompileArkTS` 的语义检查：

```
SDK 的 patched TypeScript  +  SDK 的 ArkUI 声明（ets/component/*.d.ts）  +  工程源码
```

`tools/check_arkts_types.py` 负责生成 tsconfig 并驱动
`tools/arkts_typecheck/arkts_check.js`。

> **坑（务必不要改回 CLI）**：一开始是用 `node tsc.js -p tsconfig.json` 跑的。结果
> **只要 `build()` 里出现裸 `if`，编译器就 `TypeError: node.getChildren is not a
> function` 崩掉，而且退出码是 0、一条诊断都不报**——一个静默的假阴性。

## 8. 已知差异与限制

这些是**平台能力差异**，不是未完成项；都在对应源码里写明了原因：

| 项 | 上游（libusb） | USB DDK 的实际能力 | 本移植的处理 |
|---|---|---|---|
| 读"当前配置值" | `libusb_get_configuration()` | DDK 不暴露 `bConfigurationValue` | `AppleUsbDevice::active_configuration_known = false`，不猜 |
| 切换配置 | `libusb_set_configuration()` | 无对应 API | 改用标准控制写请求 `SET_CONFIGURATION`（`bmRequestType=0x00, bRequest=9`） |
| `clear_halt()` | `libusb_clear_halt()` | 无对应 API | **显式空动作**，注释写明"做不到"，不假报已清理 |
| `recover_handshake()` | 端点停顿恢复 | 同上 | 显式空动作（同步传输模型下无端点停顿状态） |
| `cancel_pending_io()` / `clear_io_cancellation()` | libusb 异步取消 | DDK 的批量传输是**同步调用** | 显式空动作（没有在途请求可取消） |
| 拓扑身份 `topology_id` | `devpath` 末段，跨重枚举稳定 | DDK 不暴露端口链 | 用 `deviceId` 构造 `ohos-dev-%016X`；**跨重枚举不保证稳定**，已在文件头注明 |
| 设备热插拔通知 | udev monitor | 无等价物 | 由 ArkTS 侧轮询 `refreshDevices()` |

另外两处**实现选择**（不是缺陷）：

- `materialize_gpu_frame()` 在鸿蒙上只会走到"NV12 已在"的分支：`OhosVideoDecoder`
  在 AVCodec 回调里就地拷出紧打包 NV12，从不置 `DecodedFrame::gpu_frame`。
  所以没有跨设备共享纹理要"实体化"。`nv12` 为空时**如实返回 false**，让上层把这帧判为
  取不到，而不是给一张黑图。
- `materialize_gpu_frame` 单独占一个翻译单元（而不是折进 `OhosMediaBackends.cpp`）：
  折进去会把 AVCodec / OHAudio 的依赖拖进任何只想做颜色换算的目标。上游 Linux 版给了
  同样的理由。

## 9. 在 DevEco 里构建

1. **打开工程**：DevEco Studio 打开 `iPhoneMirror-ohos/`。产品配置已是
   `compatibleSdkVersion = 6.1.0(23)`、`deviceTypes: ["2in1"]`。

2. **签名**：`build-profile.json5` 里保留了一套可用的 debug 材料，当前生效的是
   `~/Documents/ohos/config/default_iPhoneMirror-ohosE-ruv-*.{cer,p7b,p12}`
   （profile 内层 `bundle-name` = `com.rayrensx.iphonemirror`，与本工程
   `AppScope/app.json5` 一致）。若 DevEco 报签名不匹配，用
   **File → Project Structure → Signing Configs** 重新自动签名。

3. **⚠️ 签名 profile 的 ACL —— 最常导致"安装直接被拒"的一条**。
   规则**不是**"受限权限都要 ACL"，要按 SDK `PermissionDefinitions.json` 里每个权限的
   `availableLevel` 与 `provisionEnable` 两个字段分别判：

   | 权限 | availableLevel | provisionEnable | 必须进 `allowed-acls`？ |
   |---|---|---|---|
   | `ohos.permission.ACCESS_DDK_USB` | `system_basic` | `true` | **是** |
   | `ohos.permission.ACCESS_EXTENSIONAL_DEVICE_DRIVER` | `normal` | `false` | 否（声明即授权） |
   | `ohos.permission.ACCESS_DDK_DRIVERS` | `system_basic` | `true` | 是（本工程**刻意不声明**） |
   | `ohos.permission.INTERNET` / `KEEP_BACKGROUND_RUNNING` | `normal` | `false` | 否 |

   查现有 profile 到底放行了什么（`.p7b` 是 PKCS#7，内层 profile JSON 是明文）：
   ```
   $ python3 -c "import re;t=open('<profile>.p7b','rb').read().decode('utf-8','ignore');\
   print(re.search(r'\"allowed-acls\".*?\]',t,re.S).group(0))"
   ```
   `ACCESS_DDK_USB` 若不在名单里，`OH_Usb_Init()` 返回 `USB_DDK_NO_PERM(201)`，
   表现为"环境自检里 USB DDK 判定 InitFailed / 一台设备都看不到"。

   **profile 由 AGC 签发（内层 `"issuer":"app_gallery"`，签名链是华为根），本地改不掉。**
   缺哪条 ACL 就只能重新自动签名（DevEco 会按 `module.json5` 的声明重新生成）。
   声明了 profile 放行不了的受限权限，安装会报
   `9568289`（`ERR_APPINSTALL_GRANT_REQUEST_PERMISSIONS_FAILED`）。

4. **构建**：`hvigorw assembleHap`（或直接点 Build）。
   `entry/build-profile.json5` 已经把原生构建接到
   `entry/src/main/cpp/CMakeLists.txt`，并传 `-DIM_PLATFORM_OHOS`。

5. **运行前的三条驱动侧约束 —— 有线采集能不能通全看这里**。

   **(a) 必须声明 vid/pid。** USB DDK 只返回"驱动配置信息里按 VID 过滤过"的设备，
   所以 `module.json5` 的 `extensionAbilities`（`type: "driver"`）`metadata` 里要配好
   Apple 的 VID `0x05AC` 与 PID 白名单，否则 `OH_Usb_GetDevices` 恒为空。
   同时该扩展的 **`exported` 必须为 `true`**：绑定它的是系统进程（扩展外设管理 SA，
   跑在 `hdf_ext_devmgr` 里、uid 不是本应用），`false` 会被框架的可见性检查挡掉。

   **(b) 客户端必须自己绑定。** 官方模型是「`DriverExtensionAbility` 通过
   `@ohos.driver.deviceManager` **被应用绑定**」，而 OpenHarmony 的 `device.cpp` 还有
   一个 `launchOnBind` 开关：`false` = 设备接入即自动拉起，`true` = **只在客户端
   `bindDevice()` 时才拉起**。所以"插上 iPhone 扩展就会起来"不成立 ——
   `entry/src/main/ets/common/UsbDriverBinder.ets` 负责这件事（幂等，空闲且系统看得见
   Apple 设备时才发起）。

   **(c) ~~DDK 只在驱动扩展的生命周期内可用~~ —— 这条在 2026-09-19 被实测推翻。**
   官方头文件给这一族 API 标的 syscap 是 `SystemCapability.Driver.USB.Extension`，
   文档也写着"仅允许 DriverExtensionAbility 生命周期内使用"，但入口 Ability 里
   `OH_Usb_Init()` 实测返回 `0`（成功）。**结论：这句话只当参考，不要据此设计架构。**
   返回码本身仍必须分开读（只报 `usb_ddk == InitFailed` 是没有用的，要看数字）：

   | `OH_Usb_Init()` 返回 | 含义 | 处置 |
   |---|---|---|
   | `0` | 成功 | — |
   | `201 USB_DDK_NO_PERM` | 权限检查失败 | `ACCESS_DDK_USB` 没进 profile 的 `allowed-acls` |
   | `27400002 USB_DDK_INVALID_OPERATION` | 连不上 DDK 服务 | 按文档是"调用方不在驱动扩展生命周期内"；**本机从未复现**，真出现再查 (b) |

   **(e) ★ `OH_Usb_Init` 与 `OH_Usb_ReleaseResource` 必须成对，且缓存"试过了"这件事
   是致命的。** 这是本项目最贵的一次自伤（`OhosUsbDdk.cpp` 的 `acquire()`）：它曾用一个
   `init_attempted` 布尔把"试过一次"钉死，本意是"失败不重试"，却把**成功**也一起钉死了。
   探针探完就 `release()`，于是**第二次 `acquire()` 起恒返回 `false`**：`QtUsbContext`
   里的 `DdkSession.ok()` 为假 ⇒ `enumerate()` 第一行就 return 空列表 ⇒
   **设备列表恒空，症状就是"软件识别不到 iPhone"**；而 `last_init_result()` 里还留着上次的
   `0`，界面于是打出"USB DDK 初始化失败：OH_Usb_Init 返回 0：成功"——
   一句自相矛盾的话，把排障方向直接带到了签名 ACL 上（浪费了整整一轮）。
   ⇒ 两条判据：**① 界面上出现"初始化失败"却带着 `0`，一律按状态机 bug 处理，不是平台问题；
   ② 凡是 `Init`/`Release` 成对的封装，引用计数归零后必须真的重新 Init。**

   **(d) 驱动扩展内只能用 DDK API**（官方《Driver Development Kit 简介》：「仅支持访问
   DDK API，不支持访问其它 ArkTS API」，未加载的模块调用会失败）。因此
   `DriverExtAbility.ets` 里的日志用内置 `console`、不用 `hilog`；状态落盘（`fileIo`）
   只是**尽力而为**，成功与否由 `write_driver_state()` 的返回值上报。
   ⇒ **"状态文件不存在"不等于"扩展没被拉起"**，界面必须按"没收到上报"陈述。

   取证手段：
   ```
   $ hdc shell "hilog | grep ImDriverExt"     # 扩展侧 console 日志 + DDK 自检结论
   ```
   扩展会在 `onInit/onConnect` 里跑一次 DDK 自检（**先 `initialize()` 再
   `getEnvironment()`** —— 不先初始化 Core，`getEnvironment` 恒返回 `-2 NotInitialized`，
   那是一个"什么都没测到"的假结论），这条结论是判断"该改架构还是该补权限"的唯一依据。

6. **权限说明（有意为之）**：`module.json5` 声明四个权限 ——
   `ACCESS_DDK_USB`、`ACCESS_EXTENSIONAL_DEVICE_DRIVER`、`INTERNET`、
   `KEEP_BACKGROUND_RUNNING`（后两个都是 `normal` 级，不涉及 ACL）。
   刻意**没有**声明两个：

   - `ohos.permission.USB_MANAGER`：本移植的 USB 通道是 DDK，完全不走
     `@ohos.usbManager` 那套服务；它是 `system_core` 级、需要 ACL。
     （仅 `common/UsbHostProbe.ets` 用 `usbManager.getDevices()` 做**旁证**诊断，
     该查询接口在 d.ts 里没有 `@permission` 标记，不需要此权限。）
   - `ohos.permission.ACCESS_DDK_DRIVERS`（2026-09-19 移除）：SDK
     `@ohos.driver.deviceManager.d.ts` 里它只挂在 `bindDriverWithDeviceId` /
     `unbindDriverWithDeviceId` 上 —— 那是**客户端**去绑定**别人提供的驱动服务端**
     用的。本应用的定位是驱动服务端本身，全部 ets 源码对它的引用数为 0；
     而它 `provisionEnable=true` 必须进 ACL，现有 profile 没有 → 安装报 9568289。
