## 1. 闸门一：ACL —— 你贴的官方文档给出了第四条路

### 1.1 先纠正一个前提

「不考虑上架」**不等于**「拿不到 ACL」。这是两个独立流程：

- **上架审核**：应用发布到应用市场时的审核。
- **受限权限申请**：AGC 侧针对某个权限的审核，颁发的是**调试 profile**（也可发发布 profile）。

官方文档原文（你贴的那段）：

> 在调试阶段，除下述方式外，还可以通过 **DevEco Studio 自动签名**完成申请。在自动签名的过程中，**将由 DevEco Studio 完成向 AGC 申请受限权限的步骤**，开发者可直接使用。

你当前用的正是 DevEco 自动签名 —— `build-profile.json5:19-32`，材料全部落在 `.ohos/config/default_*.p7b`，`type: "HarmonyOS"`。

**这条路此前没走过。** 2026-10-01 那次 9568289 的完整链条是：声明了权限 → 用的是**旧的** p7b（里面没有 ACL）→ 装包被拒 → 于是把声明移出。而不是「申请了被驳回」。

### 1.2 操作步骤（闸门一的解法）

1. **先把声明加回**（否则 DevEco 不知道要替你申请哪个权限）：
   `entry/src/main/module.json5` 的 `requestPermissions` 增加一项，
   恢复 `module.json5:190-199` 那段注释里预留的放回点：

   ```json5
   {
     "name": "ohos.permission.ACCESS_DDK_USB",
     "reason": "$string:usb_ddk_perm_reason",
     "usedScene": { "abilities": ["EntryAbility"], "when": "always" }
   }
   ```
   （`reason` 的 string 资源需同步补；若嫌麻烦可先用字面量，但要保证 `usedScene.abilities` 写的是真正调用 DDK 的 Ability。）

2. **强制 DevEco 重新走一次自动签名**：
   现有 p7b 是旧的，不重新生成就不会触发申请。做法：
   `File > Project Structure > Project > Signing Configs` —— 先取消勾选
   `Automatically generate signature`，Apply；再重新勾选，Apply。
   （更彻底：先删掉 `.ohos/config/` 下 `default_iPhoneMirror-ohos*.p7b/.cer/.p12`，再重签。）

3. **等审核结果**：AGC 通过「互动中心消息 + 邮件」通知。每个权限有各自的审核时长。

4. **验证判据**（不需要猜，界面上直接读）：
   `common/UsbPermission.ets:44` 的 `check_ddk_usb_permission()` 问的是系统令牌账本，
   它在主界面有线诊断区常显。
   - 显示 **「已授予」** ⇒ ACL 到手，闸门一通过，直接进入 §3。
   - 仍显示「未授予」⇒ profile 还没换或审核未过，**不要**急着改代码。

### 1.3 审核被驳回时的退路

文档的原话是「仅少量符合特殊场景的应用被允许申请受限权限」。我们的场景（应用自带 USB 采集驱动、接管 VID 0x05AC 设备）属于「外接设备驱动」这一类，是 DDK 设计的本意，理由正当。

若仍被驳回，则**在 HarmonyOS 商用设备上没有合规的替代通道**：
- `ohos.permission.USB_MANAGER` 是 system_core 级，比 DDK 更难，不必考虑。
- 把 DDK 调用搬进 `DriverExtAbility` **不改变**权限要求（ACL 校验是应用级的，与声明在哪个 Ability 无关）。

那时的选择只有：换 OpenHarmony 开源设备（可自签 profile、自己填 allowed-acls），或放弃有线、只保 AirPlay。

### 1.4 装包报 9568289 时，先排除这个干扰变量

`module.json5:166` 那条 metadata 写的是 `ohos.permission.ACCESS_DDK_ALLOWED`。它的名字长得像权限，但它是**驱动扩展的元数据开关**（语义：是否允许 DDK 访问），不参与 `requestPermissions` 的 ACL 校验。默认值是 false，而我们要直接用 DDK，所以**保持 true 是对的**。

唯一要动它的场合：加回 `ACCESS_DDK_USB` 声明后装包报 9568289，且你无法判断是哪一条引起的。这时**临时删掉它再装一次**，只为排除「安装器把它当权限校验」这个可能。判明之后**要放回去**。

## 2. 闸门二：驱动扩展 bind 恒 `22900001`

### 2.1 已证实的与未证实的

**已证实**（`UsbDriverBinder.ets:84-105` 有完整更正记录）：

- `onConnect` 的时间戳**不能**用来证明 bind 成功过 —— 它在 bind 完成**之前**就落盘。
  所以「扩展被拉起过」只说明懒加载生效，不说明绑定成功。
- `unbindDevice` 对「有没有残留绑定」**零信息量**：它的错误码只有 201/401/22900001，
  没有任何「不存在绑定关系」的码（那个 26300003 属于另一个 API）。
  ⇒ 用解绑返回值去证真/证伪残留，**这个实验不成立**，别再往里投入。
- 五张截图里一次「已绑定」都没出现，与「bind 从未成功、扩展每次被拉起后随即失败」一致。

**未证实**：22900001 的真实成因。官方给的方向是「设备形态是 PC/2in1、busType 合法，必要时重启设备」—— 我们的设备形态**本来就是** 2in1，这条不成立。

### 2.2 排障计划（每轮只动一个变量）

bind 的作用已经被锁定（`Index.ets:1710-1713`、`module.json5:126-131`）：**它唯一的用途是让 module.json5 里那份 VID/PID 驱动配置信息生效**，从而使 `OH_Usb_GetDevices` 不再把 iPhone 过滤掉。DDK 调用点不需要搬进扩展（入口 Ability 里 `OH_Usb_Init()` 实测返回 0，从未出现 27400002）。

按顺序试，每试一轮记一次截图 + 日志：

| 轮次 | 改动 | 看什么 |
|---|---|---|
| **B0（零改动，先做）** | 什么都不改 | 读失败文案里的**「同步抛出」还是「异步返回」**（`UsbDriverBinder.ets:308`）。同步抛出 = 服务压根没受理这次调用；异步 reject = 服务受理了但拒绝。<br>同时读文案里的 `deviceId=`：若是 0 / -1 之类，服务报 exception 就有了另一条解释 |
| B1 | `DriverExtAbility` 的 pid 列表**只留当前这台 iPhone 的 PID**（现在是 24 项） | bind 是否转 bound |
| B2 | 同一台设备**重启**后再试（官方对 22900001 的明确处置里包含这一条） | 同上 |

判据一律读 `UsbDriverBinder.ets:165` 的账本文本：
`bind 尝试 N 次 / 成功 M 次`。**M ≥ 1 才算这一轮赢了** —— 单看 summary 会被下一次失败覆盖，这正是 2026-09-19 被卡住的原因。

> **修正（2026-10-23）**：初稿把「删掉 `module.json5:166` 的 `ohos.permission.ACCESS_DDK_ALLOWED`」
> 列为第一轮，那是**方向写反了**。该 metadata 的语义是「是否允许 DDK 访问」，
> 默认值 false；本应用正是要直接用 DDK，写 `true` 是对的，删掉只会落到 false，更糟。
> 它的真正用途是**装包失败时排除干扰变量** —— 见 §1.4。

### 2.3 如果三轮都失败

说明「驱动扩展 bind」这条路在这台设备上走不通。此时应当重新审视一个假设：
**是否真的必须 bind 才能让 VID 过滤生效？**

替代验证：直接看 `OhosEnvironmentProbe.cpp:215-227` 的输出 —— 它区分了两种情形：
- 「一台设备都没枚举到」⇒ 驱动配置信息未生效（bind 缺失的表现）
- 「枚举到 N 台但没 Apple 的」⇒ 过滤已生效，问题在线材/白名单

如果拿到 ACL 后 `OH_Usb_GetDevices` 能直接看到 Apple 设备（不依赖 bind），闸门二就退化为「不影响功能」，可以把 UI 上的 bind 失败降级为提示而非阻断。

## 3. 闸门三：设备信任 —— ✅ 已实现（2026-10-30）

### 3.1 代码里能确定的

- Core 的有线采集流程**本身不发**任何 lockdown/usbmux 请求：
  USB 枚举 → 厂商 0x52 切配置 → 认领 QuickTime 接口 → bulk 收发 → 解码渲染。
  配对在 Core 里只服务于设备元数据（设备名/机型/iOS 版本），`OhosUsbMux.cpp` 是空壳也只影响这些。
- iOS 只在主机**主动发 `Pair` 请求**时才弹「信任此电脑」。插线、枚举、读序列号、切配置、连 usbmux 读 `ListDevices`/`ReadPairRecord`（只读）**都不弹**。
- **鸿蒙没有 usbmuxd，所以本工程自己当这个 usbmuxd**：USB DDK 直连 iPhone 的 usbmux 接口 → 建伪 TCP 隧道 → 在隧道上发 lockdownd 的 `Pair` 请求。

### 3.2 落地情况

| 能力 | 位置 | 状态 |
|---|---|---|
| usbmux 设备侧协议栈（mux 头、伪 TCP、端口开通） | `cpp/ohos/OhosUsbMux.cpp` | 完整 |
| lockdownd 会话 + `Pair` 请求 + 弹窗轮询 | `cpp/ohos/OhosPairing.cpp` | 完整 |
| 配对 PKI（根 CA / 主机证书 / 设备证书） | `cpp/ohos/OhosPairingPki.cpp` | 完整 |
| 配对记录持久化（插一次长期免弹窗） | `cpp/ohos/OhosPairingStore.cpp` | 完整 |
| 自动触发（检测到设备即发起） | `cpp/ohos/OhosDeviceManager.cpp` | 完整 |
| 用户可见的配对提示 | `Index.ets`（普通界面，非开发者区） | 完整 |

触发方式：**检测到设备就自动发起**（用户此前拍板）。配对记录**存到应用沙箱**（`context.filesDir`），插一次长期免弹窗。

## 5. 配对实现（2026-10-30 落地）

这一节记录实现过程中**定案的协议细节**与**踩过的坑**，避免后来者重走。

### 5.1 为什么必须自己写 usbmux

上游 `Core/` 里的 `UsbMuxClient.cpp` 走的是**本机 usbmuxd 守护进程**（unix socket /
loopback 端口），Windows 靠 Apple Mobile Device Service，Linux 靠 udev 拉起的 usbmuxd。
**鸿蒙两者都没有**，所以本工程必须自己当这个 usbmuxd：USB DDK 直连 iPhone 的 usbmux
接口（0xFF/0xFE），在设备侧实现 usbmux 协议（mux header + 伪 TCP），再在隧道上跑
lockdownd 的 4 字节大端长度 + XML plist 报文。

### 5.2 usbmux 设备侧协议的三条字节序铁律

权威依据是 usbmuxd 的 `src/device.c` 与其 README。三条都踩过：

| 事项 | 正确做法 | 踩坑后果 |
|---|---|---|
| `th_dport` | `htons(port)` **一次**。本工程 `put_u16be` 内部已做 `htons`，再套一层就双重转换 → 端口被写成 `7ef2`(32506) 而不是 `f27e`(62078) | 隧道根本连不上，弹窗永不出现 |
| `th_win` | `htons(tx_win >> 8)`（8 位缩放窗口） | 同上，窗口被写成 `0002` 而不是 `0200` |
| TCP 标志位 | 正常包**只置 ACK**（README: "all normal packets need to have flags set to ACK (and only ACK)"），不要带 PSH | 设备侧行为异常 |

另外两处记账：

- **ACK 方向**：设备回的 `th_ack` 是"设备已确认我们发出的字节数"（`tcp_tx_ack_`），
  我们发给设备的 `th_ack` 是"我们已收到设备发出的字节数"。写反了会让窗口计算错乱。
- **`rx_seq` 同步**：usbmux v2 头（`protocol/length/magic/tx_seq/rx_seq`）的 `rx_seq`
  在偏移 14，每消费一段接收数据就要写回去。
- **RST 检测**：收到 RST 要立刻判定隧道断了，不能等超时。

### 5.3 配对证书的三条编码铁律

这三处每一处都能让配对被拒，而设备侧**只回一个 `InvalidPairRecord`**，看不出原因。

1. **证书字段是 `base64(PEM 文本)`，不是 `base64(DER)`**
   依据 libimobiledevice 的 `lockdownd_pair_record_to_plist()`：

   ```c
   plist_dict_set_item(dict, "DeviceCertificate",
       plist_new_data(pair_record->device_certificate,
                      strlen(pair_record->device_certificate)));
   ```

   用的是 **`strlen`** —— 说明存的是以 NUL 结尾的**文本**（PEM），而不是带长度的二进制。
   libplist 序列化时把它 base64 进 `<data>`。本工程的 plist 实现不解码（`Type::Data`
   存的就是 base64 文本本身），所以要自己 base64 一次，**且只能一次**。

2. **设备公钥要从 PEM 转成 SPKI**
   `GetValue("DevicePublicKey")` 返回的是 `<data>`，内容是 `base64(PEM)`，PEM 标签是
   `"RSA PUBLIC KEY"`（PKCS#1 的 RSAPublicKey）。而证书里的 `subjectPublicKeyInfo`
   字段要的是 **SPKI** —— 差一层 `AlgorithmIdentifier` 包装。直接嵌 PKCS#1 会让设备
   解析证书时结构错位。

   判据：SPKI 的第一个子元素是 SEQUENCE，PKCS#1 的是 INTEGER。

3. **`extensions` 字段少一层 `SEQUENCE OF`**
   RFC 5280：`Extensions ::= SEQUENCE SIZE (1..MAX) OF Extension`，而 `[3] EXPLICIT`
   装的是**这个 SEQUENCE**。所以实际字节是 `A3 <len> 30 <len> 30 <ext1> ...`。
   少了中间那层，OpenSSL 直接报 `asn1_check_tlen: wrong tag (Type=X509_EXTENSION)`，
   设备侧则表现为"证书被拒"。

   这一处是靠 `tools/pairing_der_selftest.py` 抓出来的（脚本现场从 C++ 源码里读
   tag/OID 常量与结构，产出证书交给 OpenSSL 判定）。

### 5.4 其余定案

| 事项 | 结论 | 依据 |
|---|---|---|
| 摘要算法 | 按设备版本选：`ProductVersion` < 4.0.0 用 SHA1WithRSA，否则 SHA256WithRSA | pymobiledevice3 的 `select_hash_algorithm()` |
| 设备公钥取法 | 必须**探测** SDK 的 `"X509"` 输出是 SPKI 还是 PKCS#1，不能无条件包装 | SDK 文档只写 "Supports X509"，没写产出形态 |
| `WiFiAddress` | 必须在 `Pair` **之前**取；晚了在 iOS 7 上会失败并导致设备重连 | libimobiledevice `lockdownd_do_pair()` 的注释 |
| `EscrowBag` | 在 `Pair` 响应的**顶层**，不在 `PairRecord` 里 | libimobiledevice `lockdownd_do_pair()` |
| 弹窗轮询 | 收到 `PairingDialogResponsePending` 要**继续重发**（本工程 1.2 秒一次） | usbmuxd issue #281：preflight 不重试就失败 |
| `HostID` | 必须**稳定**（复用已存记录），否则设备每次都当新电脑 → 每次弹窗 | 设备侧记的是「HostID + 根 CA 公钥」 |
| 根 CA | 必须**复用**同一把私钥（同上） | 同上 |

**★ 关于 mode：只探测，不切换。**
上游 usbmuxd 探测完会按需 `SET_MODE(0x52)` 切回 initial mode（默认 mode 1），
因为它**独占**设备、只做 usbmux。本工程的采集链路依赖 mode 2 的 Valeria 配置
（`0x2A` 接口），配对期间把它切走会打断正在进行的采集 ——
「采集优先」还是「配对优先」是产品决策，不是协议问题，所以不代劳。

另外，上游 `usb.c guess_mode()` 判定 mode 2 (Valeria) 的条件是
`has_valeria && has_usbmux`，mode 3 (CDC-NCM) 是 `has_cdc_ncm && has_usbmux` ——
即「切到采集配置后 usbmux 接口仍然存在」是**上游自己的前提**。
所以"设备停在 mode 2 导致 usbmux 不响应"这个说法不成立。

### 5.7 诊断粒度（2026-10-30 补）

「插线没反应」要在真机上一次插线就定位到环节，诊断日志必须能区分这些**互斥**的失败：

| 失败点 | 诊断日志里长什么样 |
|---|---|
| 设备没被 DDK 枚举到 | 诊断区「DDK 原始读数」`设备总数=0` |
| 设备被枚举但 PID 不在名单 | `设备总数>0` 但 `Apple=0` |
| 描述符里没有匹配的接口 | `未找到 usbmux 接口（0xFF/0xFE/2）：活动配置=N，描述符里的接口如下` + 逐条 `配置=… 接口=… class=… subclass=… protocol=… 端点:[…]` |
| 接口匹配但端点不成对 | 同上，但能看到该接口的端点列表里缺 IN 或缺 OUT |
| 接口在，但 DDK 认领被拒 | `认领候选失败：配置=… 接口=… alt=… in=0x.. out=0x.. 返回=<码>`（每个候选一行） |
| 认领成功 | `已认领 usbmux 接口：配置=… 接口=… alt=… in=0x.. out=0x..（候选 1/N，活动配置=…）` |
| 版本握手失败 | `usbmux 版本握手超时：设备没有回应版本请求` |
| 隧道建立失败 | `usbmux 隧道打开超时：设备没有回应 SYN` / `设备拒绝了到端口 62078 的连接（RST）` |
| 设备不是 lockdownd | `设备侧服务不是 lockdownd（Type=…），无法配对` |
| 弹窗已出、等人点 | `弹窗已出现在 iPhone 上，等待你点「信任」…` |
| 证书被拒 | `配对被设备拒绝：InvalidPairRecord` |

**★ 关键**：上面第 2 行与第 3 行之间没有中间态。
`Apple=0` 时配对代码**根本没被执行**，此时去查配对相关的任何东西都是空转。
**先确认 `Apple=` 的值，再往下看。**

## 5.8 usbManager 备用通道（2026-10-31 落地）

### 5.8.1 为什么要有第二条路

DDK 通道有两个绕不开的闸门：`ACCESS_DDK_USB` 要进签名 profile（闸门 1，已解），
设备要驱动扩展 bind 之后才出现在 `OH_Usb_GetDevices()` 里（闸门 2，恒 22900001）。
`@ohos.usbManager` 这条路两个闸门都没有：

- 权限存在**设备级 DB 记录**里（`UsbRightManager`），由 `requestRight()` 弹一次
  系统授权窗换来，**授权一次长期有效，不查签名 ACL**；
- `getDevices()` **不按 VID 过滤**，不需要驱动扩展。

### 5.8.2 数据通路

```
ArkTS（UsbManagerHost.ets）             native
  getDevices() → 筛 0x05AC
  requestRight(device.name) ← 弹窗（仅首次）
  connectDevice(device) → pipe
  getFileDescriptor(pipe) → fd ────────→ OhosUsbMux::connect_fd(fd)
                                          ├─ discover_usb_fd_mux()：读设备/配置描述符、
                                          │   定位 usbmux 接口与 bulk 端点、读 UDID、
                                          │   必要时 SET_CONFIGURATION
                                          ├─ 版本握手（与 DDK 路径共用）
                                          └─ 配对（OhosPairing::request_device_trust_fd）
```

- fd 是系统 USB 服务 `open("/dev/bus/usb/BBB/DDD", O_RDWR)` 后经 IPC 复制进本
  进程的标准 **usbfs** 节点描述符；native 用 `USBDEVFS_BULK/CONTROL` ioctl 直收直发。
- **明确不调 `usbManager.claimInterface()`**：那个 claim 是服务侧 libusb 的，会占掉
  `intf->dev.driver`；native fd 路径靠内核 usbfs 的 per-fd 记账（`proc_bulk → claimintf`），
  两条路径混用会互相顶掉。
- 内核语义要点（openharmony/kernel_linux 源码级确证）：`bulk.ep` 是**完整端点地址**
  （含 0x80 方向位）；端点只从**活动配置**里找（`findintfep` 只遍历 `dev->actconfig`）；
  vendor 与 device-recipient 控制传输免认领；`usb_bulk_msg` 超时会 kill URB
  **丢弃已收部分数据** ⇒ 读必须按端点包长请求；载荷恰好是包长整数倍要补 ZLP。

### 5.8.3 UDID 从哪来

非系统应用的 `getDevices()` 把 `serial` 清空（`UsbHostManager::GetDevices()` 对非系统
应用 `dev.SetmSerial("")`）。SDK 文档明说：授权后**自己发控制传输**取。`connect_fd()`
的发现阶段读设备描述符 + iSerialNumber 字符串描述符，读到与 DDK 路径**同一个**
UDID，两条路径的配对记录因此互认（`OhosUsbMux::fd_serial()`）。

### 5.8.4 触发与去重

- UI 心跳（`Index.ets::refresh_usb_environment`）检测到系统 USB 服务可见 Apple 设备
  且无采集会话时，调 `attempt_usb_fd_channel()`；失败冷却 10s，授权被拒冷却 60s。
- `UsbManagerHost.ets` 内部 `channelBusy` 防叠开；同设备 fd 缓存复用。
- native `JsPairViaUsbFd` 用 `atomic` 保证进程内同时只跑一轮 60 秒配对。

### 5.8.5 待真机验证

无设备连接，以下只能插线后确认：① 2in1 上 `usbManager` 能力是否开放（801 判别）；
② `requestRight` 授权窗能否拉起；③ fd 上的 ioctl 是否被 SELinux 放行；
④ 切配置/读描述符的实际表现。
