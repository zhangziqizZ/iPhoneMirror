## 零、一句话结论

上游 1.8.5-pre2 这一轮**主要是 Windows 侧的稳定性与反控加固**（USB 后端打包、DDI 缓存、
RemotePairing、键盘钩子续期、PyInstaller 桥），**对我们 99% 不适用**。

真正值得跟进的只有 **3 条**，且都集中在「**没有新帧 / 坏帧时不要黑屏**」这同一个主题上：

1. 🟢 手机静止不发视频时**保留最后一帧**（且帧不活跃**不再重启会话**）
2. 🟢 静态预览**重绘失败重试** + 遮挡时节流 + **仅成功后才标记 presented**
3. 🟡 繁体中文（**台湾**）独立本地化 —— 我们目前繁体只覆盖香港

上一份报告列的六大缺口（截图/全屏/i18n/视频投屏/录制/多设备）**优先级不变**。

## 一、🟢 值得跟进（按性价比排序）

### 1. 手机静止不发视频时保留最后一帧

**上游（1.8.5-pre · Fixed）原文要点**

> Keep the last wireless mirroring frame visible when a static phone screen
> stops sending video. Frame inactivity no longer restarts the session, and
> resized or additional previews can reuse the retained frame.

即三条行为：
- 手机屏幕静止、停止发送视频 → **最后一帧继续可见**（不黑屏）
- **帧不活跃不再重启会话**（这是关键：以前可能把"没帧"当成故障去重启）
- 预览被 resize、或新增预览窗口 → **可复用保留的那一帧**

**我方现状**

- `OhosPreviewRenderer.h:143-147` 有 `last_frame_w/h/bytes/format/stride` —— 但这只是**诊断字段**
  （`OhosPreviewRenderer.cpp:818-822` 填进 diag 快照，最终显示在状态行 `末帧 WxH·NB·fmtN`），
  **不是"保留显示"行为**。
- 渲染策略是「只留最新一帧」（1.0.43 起的丢帧保实时策略），**没有"末帧保持"的显式逻辑**。
- 1.0.63 做的是 **no-IDR 边界自愈**（配置包缺 IDR 时截短非 IDR 帧），与"手机静止不发帧"
  是**两个不同的场景**。

**价值**：直接对应我们长期困扰的「黑屏 / 不显示」类问题的**又一个成因**。
我们此前已归因过：着色器（1.0.62 澄清无罪）、IDR 缺失（1.0.63）、硬解零像素（进行中）。
「手机静止 → 我方判定为异常」是**尚未排查过的一条**。

**建议动作**：渲染器加「末帧保持」——无新帧时继续呈现上一帧，且**不触发会话重启**；
resize / 独立预览窗口创建时复用该帧。
可与正在做的「硬解零像素重试」**合并为同一条工作线**（主题一致：坏帧/无帧不黑屏）。

**成本**：中低。**风险**：要注意别把「真的断了」也当成「静止」，需保留超时判据。

### 2. 静态预览重绘失败重试 + 遮挡节流 + 仅成功后标记 presented

**上游（1.8.5-pre · Fixed）原文要点**

> Retry static preview redraws after a busy compositor or a transient GPU
> upload failure, including when opening settings resizes the preview. Only
> mark a frame as presented after success, and throttle retries while occluded.

三条要点：
- 合成器忙 / GPU 上传**瞬时失败** → 重试（含"打开设置导致预览 resize"这一具体触发场景）
- **仅在成功后才把帧标记为已呈现**（避免"标了 presented 但实际没画上"的自我欺骗）
- **遮挡时节流重试**（窗口不可见就别疯狂重试）

**我方现状**

- 只有**推帧侧的 surface attach 重试**：`OhosPreviewRenderer.cpp:51-52` 注释
  「最多 `kPreviewReattachMax` 次、每次间隔 ≥ 1 秒」，`721-750` 实现
  （`retry_surface` → `attach()`）。
- **没有**「仅成功后标记 presented」的语义。
- **没有**「遮挡时节流」。

**价值**：与我们正在做的硬解零像素重试**同源**，且上游明确点出了
「打开设置 resize 预览」这个我们也会遇到的具体触发路径。

**建议动作**：在现有 attach 重试基础上补两点——① 只有 EGL 交换/上传真正成功才置 presented 标记；
② 增加遮挡/不可见时的重试节流。

**成本**：中。**风险**：presented 语义改动会影响现有 diag 读数口径，需同步改诊断展示。

### 3. 繁体中文（台湾）独立本地化

**上游（1.8.5-pre · Added）原文要点**

> Add independent Traditional Chinese (Taiwan) localization across the app,
> driver tools, installer, stream test pages and complete release history.

上游在原有繁体之外**新增独立 zh-TW**（与既有繁体区分）。

**我方现状**

`entry/src/main/ets/common/i18n.ets`：

```ts
/** 0=跟随系统 1=简体 2=繁中(香港) 3=英文。 */
export const LANGUAGE_TAGS: string[] = ['system', 'zh-CN', 'zh-HK', 'en-US'];
```

繁体**只覆盖香港（zh-HK）**，**没有台湾（zh-TW）**。
资源目录也只有 `base`（`entry/src/main/resources/` 与 `AppScope/resources/` 均只有 base），
运行时多语言全靠 `i18n.ets` 查表，不走 resources 限定目录。

**价值**：取决于目标用户是否含台湾。港台繁体用词有实际差异（如「軟體/軟件」「網路/網絡」），
对台湾用户而言 zh-HK 译文是**可感知的不准确**。

**建议动作**：若需要，`LANGUAGE_TAGS` 加 `'zh-TW'`（索引 4），三处
`LANGUAGE_LABELS` 各加一个「繁體中文（台灣）」标签，再补一套 zh-TW 词典。
**机械工作，不改逻辑。**

**成本**：低-中（主要是一套词典的翻译量）。

## 二·5、🟢 系统托盘（鸿蒙 PC 官方方案）—— 更正后新增

> 初稿写「鸿蒙无系统托盘概念，N/A」是**错的**。鸿蒙 PC 有官方托盘/状态栏方案，
> 且它还是**官方认可的后台保活手段**。这一节重新评估。

### 平台能力（鸿蒙 PC 官方）

- `StatusBarViewExtensionAbility`（`@kit.StatusBarExtensionKit`）+ `statusBarManager.addToStatusBar()`
  添加状态栏图标；图标 24vp×24vp，需提供 **white / black 两套** PixelMap（适配深浅色状态栏）。
- 左键：可弹窗（`quickOperation.abilityName`）或直接 `showAbility()` 唤回主窗口。
- 右键：可挂 `statusBarGroupMenu` 多级菜单（`notifyOnly` + `menuCode` 回传业务）。
- `statusBarManager.on('statusBarIconClick')` 监听点击，`iconClickType` 区分左右键。
- **后台保活增强**：`startAbility` 时传
  `processMode: NEW_PROCESS_ATTACH_TO_STATUS_BAR_ITEM` +
  `startupVisibility: STARTUP_HIDE`，可拉起一个**绑定托盘图标的新进程**并隐藏启动
  —— 这是鸿蒙 PC 上「让后台进程既可见、又可退出、还不会被系统 kill」的官方解法。
- 官方文档：<https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/statusbar-extension-guide>

### 我方现状

- `grep statusBar|StatusBar|托盘|Tray` **零命中** —— 工程**完全没有**托盘相关代码。
- 现有保活是**另一套**：`entry/src/main/ets/common/BackgroundKeepAlive.ets`
  走 `backgroundTaskManager` **长时任务**（需 `KEEP_BACKGROUND_RUNNING` 权限 +
  `abilities[].backgroundModes: ["dataTransfer"]`，两者已在 `module.json5` 声明），
  并配一条常驻通知（WantAgent 点击回主 Ability）。
- 该文件注释已写明痛点：*「投屏时用户一定会把 App 切到后台……没有长时任务，鸿蒙会冻结
  整个进程，AirPlay/mDNS 响应器的收发线程随之停摆」*，且故障极具迷惑性
  （`mdns_answered` 是累计值，回前台看到的仍是历史数字）。

### 价值判断：值得做，但**不能按官方"增强用法"做**

| 目标 | 结论 |
|---|---|
| ① 状态栏图标 + 左键唤回主窗口 + 右键菜单（退出/开始投屏等） | ✅ **可以做**。纯 UI 层，不碰采集链路 |
| ② 关闭主窗后从托盘唤回（配合 `onPrepareToTerminate` 返回 true 拦住关闭） | ✅ **可以做**，是真实体验补完 |
| ③ **用托盘绑定的新进程承载 AirPlay 接收**（官方增强用法 1） | ⛔ **不能做**，见下方硬冲突 |

### ⚠ 硬冲突：渲染器是进程级单例

`module.json5` 里 `StandalonePreviewAbility` 的注释已经把这条约束写死了：

> 刻意**不给** process 字段 ⇒ 它跑在默认进程（同 EntryAbility）。这是**必须**的：
> 预览画面来自 `libim_core.so` 里的渲染器单例（`OhosPreviewRenderer` 只有一个 EGLSurface），
> **换了进程就是另一份 so 实例，`im_attach_preview_window()` 根本挂不到画面**。

因此「把 AirPlay/mDNS 挪进托盘新进程」会直接导致**预览画面挂不上**：
- 上游 Windows 之所以能这么做，是因为它是**独立 `WirelessHost.exe` + 命名管道 IPC**
  把画面回传主进程（见上一份报告 § 二「无线宿主」一行）。
- 我们是**同进程直驱** vendored airplayserver，没有这层 IPC。

**要做 ③，必须先补一层跨进程画面回传（共享内存/软解码回传），那是架构级大改**，
不亚于「多设备」。建议**明确后置**，不要和托盘绑在一起做。

### 建议落地顺序（若决定做）

1. **先只做纯 UI 部分**：托盘图标（white/black 两套）+ 左键 `showAbility()` + 右键菜单，
   **保留现有长时任务保活不动**。这一步零风险、可独立验证。
2. 观察托盘是否能让长时任务更稳（用户可见 ⇒ 降低被系统回收的概率），
   **先只做观察，不切换保活机制**。
3. 若确实要进程级保活 → 先立项「跨进程画面回传」，再回头做增强用法。

### 与上游的对应关系

上游这一轮（1.8.5-pre Fixed）有两条托盘相关修复：

- 「托盘启动后导航/按钮图标颜色与控件同步」→ WPF 视觉树专有，**不适用**。
- 「托盘启动后恢复主预览有线/无线触控（从 native window handle 初始化输入源）」
  → 依赖 WPF handle，**不适用**；但「**从托盘唤回后预览要能恢复**」这个诉求
  **对我们同样成立**，且正好和 § 一·1「保留最后一帧」互补（唤回时直接复用保留帧）。

## 三、⛔ 平台专属，明确不跟进

| 上游新增 | 不跟进理由 |
|---|---|
| **键盘映射向导 + 五点触控**（1.8.5-pre Added） | 依赖 Windows 键盘钩子与多指 HID。**我们蓝牙反控仍是「单指指针 + 键盘」实验阶段**，iPhone 端甚至可能不出指针。多指是下一步之后的下一步 |
| **UxPlay 可选下载组件**（1.8.5-pre Added） | 我们 vendored `airplayserver`（combined-mode 血统）并自研 mDNS 响应器，不需要外部可选后端 |
| **多设备键盘写入隔离**（1.8.5-pre Fixed） | 我们是**单会话单例**架构（`startCapture/stopCapture` 进程级），多设备是后置的架构级改造（要把渲染器/解码器/采集全部按会话实例化） |
| **系统托盘启动相关**（图标颜色同步、托盘后恢复触控、从 native handle 初始化输入源） | ~~鸿蒙无系统托盘~~ **初稿判断错误，已更正**。鸿蒙 PC **有**官方托盘方案（见 § 二·4）。但「图标颜色同步」「从 WPF 视觉树 handle 初始化输入源」仍是 WPF 专有，不适用；**「托盘唤回主窗口」可跟进** |
| **Unreleased 几乎全部**：x64 libusb0 DLL 打包进 `_internal`、Apple DDI personalization/缓存镜像、RemotePairing 有界重试、USB 端口自动重连、Windows 键盘钩子自动续期、PyInstaller bridge 序列化、capture-mux listener 超时 | 全是 **Windows/驱动/PyInstaller/WPF 专属**。且我们 **USB 通道因 `ACCESS_DDK_USB` 是 `system_basic` ACL、调试 profile 改不了而整体不可用**（已从 `module.json5` 移除），这些与我们无关 |

> 说明：Unreleased 段落（CHANGELOG 6-94 行）约 90 行，逐条看下来**没有一条**能映射到鸿蒙侧。
> 这符合预期——上游 1.8.x 的重心是有线反控与 DDI，正是我们因平台/权限无法还原的那一块。
